### Host the Frontend and Media with Amazon S3 & CloudFront

This section creates separate S3 storage for frontend assets and uploaded media, deploys the React production build, and distributes the website through Amazon CloudFront.

#### Step 1 — Create the S3 buckets

Open **Amazon S3 → Buckets → Create bucket** in `us-east-1` and create separate buckets for distinct purposes:

- `startups-blogs-frontend`: stores the compiled React frontend.
- `startups-blogs-media`: stores business logos, avatars, cover images, and other uploaded media.

Bucket names are globally unique, so use an available suffix if either name is already taken. Keep **Object Ownership** set to **Bucket owner enforced**.

For production, keep **Block Public Access** enabled and grant CloudFront access to the frontend bucket through **Origin Access Control (OAC)**. The screenshot shows public access being disabled for a bucket; use that only for a deliberate public-hosting design with a narrowly scoped bucket policy. The media bucket should not be made broadly public by default.

#### Step 2 — Configure CORS

Open the appropriate bucket, select **Permissions → Cross-origin resource sharing (CORS)**, and add a rule for the actual application origins. During testing, the screenshot uses a wildcard origin and multiple methods:

```json
[
  {
    "AllowedHeaders": ["*"],
    "AllowedMethods": ["GET", "PUT", "POST", "DELETE"],
    "AllowedOrigins": ["https://<CLOUDFRONT_DOMAIN>"],
    "ExposeHeaders": []
  }
]
```

Replace `<CLOUDFRONT_DOMAIN>` with the deployed frontend origin. Add `http://localhost:5173` only when local development requires direct browser access. Avoid `AllowedOrigins: ["*"]` in production when upload or authenticated requests are involved.

#### Step 3 — Verify the project buckets

Return to the S3 bucket list and verify that the project buckets exist in `us-east-1`. The evidence shows `startups-blogs-frontend`, `startups-blogs-media`, and an additional project bucket.

Use the frontend bucket only for generated static files. Upload media through the protected NestJS `POST /upload` endpoint so the backend can validate ownership, MIME type, and file size before writing to S3.

#### Step 4 — Build and upload the React frontend

Set the production API URL, build the Vite application, and upload the generated `dist` directory:

```bash
cd frontend
npm ci
npm run build
aws s3 sync dist/ s3://startups-blogs-frontend --delete
```

Do not upload frontend source files, `.env` files, access keys, or backend secrets. After later deployments, create a CloudFront invalidation so users receive the new `index.html` and assets:

```bash
aws cloudfront create-invalidation \
  --distribution-id <DISTRIBUTION_ID> \
  --paths "/*"
```

#### Step 5 — Create the CloudFront distribution

Open **Amazon CloudFront → Distributions → Create distribution** and configure:

- **Origin:** the `startups-blogs-frontend` S3 bucket.
- **Origin access:** Origin Access Control (recommended).
- **Viewer protocol policy:** Redirect HTTP to HTTPS.
- **Default root object:** `index.html`.
- **Allowed methods:** `GET` and `HEAD` for the static frontend.

Update the S3 bucket policy with the OAC policy generated by CloudFront. Wait until the distribution status becomes **Enabled** and deployment finishes.

#### Step 6 — Configure React Router fallback

Because React Router performs client-side routing, direct requests to application paths may return `403` or `404` from S3. In **CloudFront → Distribution → Error pages**, create these custom error responses:

| HTTP error code | Response page path | HTTP response code | Minimum TTL |
|---|---|---:|---:|
| `403` | `/index.html` | `200` | `10` seconds |
| `404` | `/index.html` | `200` | `10` seconds |

After saving, open the CloudFront domain and test both the home page and a nested route such as `/businesses`.
